## Governing contracts and source evidence

ADR012 is accepted for v2 source implementation only. It selects a strict `/v2/publish/{kind}` JSON envelope; skills carry their exact original ZIP as base64 and the other kinds carry typed raw JSON; the frozen v1 bytes remain unchanged. Immutable identity is authenticated workspace plus kind plus idempotency key. The same key and exact immutable identity replays the original result, a changed payload conflicts, and the same ID/version/bytes under another key returns the existing admission exactly once. Revoked versions cannot be revived. Every replay must first pass the caller's current membership/policy check. The full serialized success response and effective client/server budget must be decided before any mutation. One catalog admission and one `version_published` outbox event commit atomically. Original bytes and digest distinctions must survive restart.

The plan's PUBLISH.0 acceptance specifically requires exact contracts, a bounded write set, tenant-safe staging ownership/retention/reconciliation, and qualification of actual fixtures. ## Recommended coherent staging and ownership design

Keep existing global digest objects and the existing digest field as content identity for legacy data and consumers. For v2, add an immutable, tenant-safe physical **attempt object key** such as `v2/<random-opaque-attempt-id>/<artifact-digest>` under the configured store prefix. Never derive a physical key from caller strings. The key is created and written only by an attempt that owns its durable database row. Store the exact key in the durable v2 publication/catalog reference and read it after restart; do not infer a v2 physical key from the digest. A global content digest remains a value, not proof that this publication owns or may delete the global blob.

Use a durable RLS-protected `publication_attempts` row keyed by `(workspace_id, kind, idempotency_key)` as the permanent idempotency ledger. It records request identity (descriptor ID/version and exact immutable blob digest/length; digest is backed by verified exact source bytes), canonical admitted response bytes, opaque object key, state, and timestamps/lease. A uniqueness constraint separately on `(workspace_id, kind, artifact_id, version)` or equivalent catalog uniqueness arbitrates different idempotency keys for one immutable version. Retain the identity/result tombstone for at least the immutable version's lifetime; safest default is permanent while that version or revocation record exists. Do not use a short idempotency TTL.

Create the attempt row in a short principal-bound transaction **after** complete envelope/type/byte validation, current policy and namespace/admission checks, and complete response serialization/budget check, but before object PUT. Its opaque key and upload lease are committed before storage I/O. PUT uses immutable create-if-absent semantics and verifies exact size and SHA-256. A retry for the same attempt/key writes the same key and same bytes; a different payload conflicts before PUT. Once PUT succeeds, publish in one `WithTenantPrincipal` transaction: lock the attempt row; recheck matching identity and current policy generation where applicable; verify its staged state; insert catalog version with both content digest and exact attempt object key; insert durable artifact-to-object reference/mark attempt committed; store replay response and permanent identity; and append exactly one outbox event. Unique constraints arbitrate races. Same-key retries of a committed row return its saved result only after fresh HTTP authorization. Same ID/version/bytes with a different key returns the canonical existing result and records that alias in the same transaction without another event. Different bytes conflict regardless of key. Revoked version state conflicts. On outbox/catalog/commit failure the transaction rolls back all catalog/reference/replay/event effects; the precommitted attempt row and physical object remain owned and eligible for retry or later cleanup.

Use an explicit `staged -> committed` state transition plus lease. A cleanup worker claims only expired staged attempts with `FOR UPDATE SKIP LOCKED`, verifies no committed catalog/reference row points to their exact object key, marks a bounded deletion claim/lease, commits that claim, then deletes that exact owned key and marks the attempt `deleted` in a second transaction. On delete failure, retain retryable state and backoff; never mark deleted before successful deletion. If a process dies after claim but before delete, lease expiry makes that same owned key retryable. If it dies after delete but before recording success, retry delete treats not-found as success. If a concurrent publisher commits, it must lock the attempt row and win the staged-to-committed transition; cleanup either sees committed and skips, or its deletion claim prevents publication from committing and causes publication retry. Do not delete by digest prefix/listing or from catalog absence alone. Do not delete global legacy digest objects, another attempt's key, or a committed reference, even if another row has the same content digest.

Set upload lease from database time (recommendation: 24 hours, renewable only by a matching authorized retry); record `created_at`, `lease_expires_at`, cleanup claim, attempt count and last error class. Keep committed object retention tied to catalog/version retention, not the orphan lease. Current catalog/version and event retention are distinct; no catalog deletion lifecycle exists here, so committed objects default to indefinite retention. Reconciliation must re-read durable attempt/catalog references after restart and handle: row without object (same-key retry can PUT); owned object without successful catalog admission (retry or expire/cleanup); committed reference with missing object (integrity/readback failure and alert, never silently recreate from JSONB); and object whose key has no durable owned row (foreign/unowned, never delete). Request cancellation before the initial row leaves no physical object. Cancellation or timeout after row or during/after PUT leaves an owned, leased attempt for retry/reconciliation; cancellation during SQL rolls back its transaction. The client receives an honest unknown outcome if commit result is ambiguous and safely retries with the same idempotency key.

This satisfies owned cleanup by avoiding shared-object deletion. It does require a new exact-key backend operation and delete operation restricted to the generated key carried by a durable owned attempt; current `Put`/`Bind` and current no-delete API do **not** satisfy those physical gates. File backend should create/verify within the store root using opaque generated path components and atomic create; S3 backend should conditionally create the same attempt key and issue delete only through the claimed owned-key operation. The caller must never supply a raw key.
