# Gist enrollment decision brief — 2026-10-04

**Recommendation for founder decision:** use GitHub sign-in to establish human identity, admit people only by explicit invitation to one private Gist workspace, and let the Gist authorization server issue bounded workload grants only under an operator-approved parent grant. Keep this as a proposed enrollment choice until the founder accepts it; this brief does not complete T-GR-SCOPE.4.

## Proposed choice

Use a GitHub App for browser sign-in, with no repository, organization, enterprise, webhook, or installation permissions. Use its user-authorization flow only to obtain the authenticated GitHub profile, persist the durable GitHub numeric `id` as the subject (namespaced as GitHub), and discard the GitHub user token after identity verification. Do not treat `login`, display name, or email as an authorization key. GitHub recommends persisting the durable `id`; it says handles and email addresses can change. [GitHub OAuth app best practices](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/best-practices-for-creating-an-oauth-app) and [GitHub REST API: authenticated user](https://docs.github.com/en/rest/users/users#get-the-authenticated-user).

Prefer a GitHub App over an OAuth App for this sign-in-only role. GitHub Apps start with no permissions, and a GitHub App user access token can call `GET /user` without additional permissions. Its user token expires after eight hours by default; Gist needs it only long enough to verify identity, so do not request or store a refresh token. An OAuth App is a simpler alternative, but GitHub describes OAuth App tokens as long-lived by default unless expiration is enabled, and it cautions that OAuth Apps can request user-wide access. [Choosing GitHub App permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app), [GitHub App user access tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app), and [GitHub App/OAuth App differences](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps).

Register one exact HTTPS callback: `https://gist.sire.run/auth/github/callback`. Do not register wildcard callbacks or accept a callback URL from a request. For every login, generate one-use random `state` and PKCE `code_verifier`; send `code_challenge_method=S256`, bind both values to the initiating server session, check and consume `state` once on return, and exchange the code only after those checks. Keep the authorization code and GitHub token out of browser storage and logs. Use a `Secure`, `HttpOnly`, `SameSite=Lax` session cookie and rotate the Gist session after login. Accept a post-login return path only when it is a normalized relative path on `gist.sire.run`; reject absolute URLs, scheme-relative paths, and encoded host changes. GitHub marks `state`, exact `redirect_uri`, and PKCE S256 as strongly recommended and warns that wildcard callbacks can expose codes to unintended hosts or paths. [GitHub authorization flow and callback rules](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps) and [GitHub App user authorization flow](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app).

After GitHub identity verification, require a valid owner-issued invitation bound to the GitHub numeric subject and the single private workspace. Invitations should expire, be single-use, and redeem atomically. A successful GitHub sign-in alone never creates a user, workspace, membership, or operator role. Keep one controlled founder/operator enrollment path tied to a verified GitHub sign-in and a pre-approved durable subject; disable that path once the workspace owner is established. Do not provide public bootstrap or manual SQL seeding.

The verified human session may request workload authority only inside the invited workspace. The workload parent grant is issued by the designated operator and bounds subject, workspace, actions/scopes, resource audience, policy generation, and expiry. Child grants must be subsets of the parent at mint and use time and must be revocable and auditable. Human GitHub sign-in does not supply a provider credential and does not grant execution by itself.

## Keep three credentials separate

Store the GitHub App client secret and the Gist consent-signing secret as separate, operator-controlled AWS Secrets Manager entries with distinct IAM access, rotation, and audit. The GitHub client secret is used only for the server-side authorization-code exchange. The consent/signing secret belongs to the selected Gist authorization server and protects its consent or grant records; it must never double as the GitHub client secret, cookie key, OAuth `state`, workload bearer token, or provider credential. Generate `state` independently for each authentication attempt. Do not retain a GitHub user access or refresh token after resolving the numeric subject.

GitHub is the upstream human identity source in this proposal. Gist's configured authorization server remains responsible for consent, workload grants, refresh/revocation, and Gist token signing; it remains the issuer for Gist workload access. Composio is a separate provider-connection/credential route for a user's selected integrations. Neither a Composio account nor a GitHub sign-in is a Gist workload grant. Existing Treg or Composio accounts do not by themselves qualify either service as Gist's identity provider or OAuth authorization server. If an external service is proposed as Gist's authorization server, it still must pass the RFC-002 issuer conformance gate before deployment; this brief does not make that selection.

## What remains for deployment

The founder must accept or revise this recommendation and prove the intended operator identity through the live GitHub sign-in before it receives operator authority. The deployment owner must then create and own the GitHub App, confirm that its authorization availability covers the intended invitees, register only the exact callback above, disable wildcard matching, enable expiring user tokens, and confirm the app has no data permissions or subscriptions. The operator must identify the one workspace, the invite issuer, the approved founder subject ID, the human callback/token custodian, and the workload-parent grant authority. The AWS owner must confirm the target account/region, create the two Secrets Manager entries, and bind access narrowly to the runtime and authorized custodians. Route/TLS readiness for `gist.sire.run`, actual callback handling, secret rotation/revocation, session security, invitation denial cases, and workload-parent enforcement remain implementation and live-acceptance gates. No GitHub app, AWS secret, account, permission, or provider connection was created or changed for this brief.
