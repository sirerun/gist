# RFC-003: Gist Execution Gateway — Governed Execution, Credential Custody, Billing

- **Status:** Draft. Split out of RFC-002 rev 1 (2026-09-25) after external
  design review found the registry and gateway concerns conflated in one
  document. **Not yet reviewed as its own document** — the content below
  inherits the registry review's keep-list but needs its own review pass and
  its own threat-model sign-off before any implementation milestone is
  scheduled. Revised 2026-09-25 to scope the gateway to runtime-less clients
  and to align its execution-evidence vocabulary with the protected-effects
  engines that consuming runtimes already own (§3).
- **Updated:** 2026-09-25
- **Depends on:** RFC-002 (`docs/rfc-002.md`) — the registry, its data model,
  and its authorization model (§12 ADR). Nothing here is buildable until the
  registry contract is frozen at M1.
- **Provisional service origin:** same Gist deployment as RFC-002
- **Consumers:** agent runtimes and clients that report `requires_gateway`

## 1. Purpose

RFC-002 ships a registry: discovery, retrieval, and resolution. It deliberately
excludes execution — a registry can ship with zero executable providers, and
consuming runtimes already execute against providers directly. RFC-003 covers
the case RFC-002 explicitly refuses to fake: a client whose runtime cannot
execute a resolved capability (`requires_gateway`), and the governed execution
service that would serve it.

The gateway is Gist executing an approved capability on a provider on behalf of
a principal, inside a ledgered, approval-gated, billed pipeline. It exists only
where the registry has already established identity, binding, and trust; it
introduces no new identity system.

## 2. Scope moved here from RFC-002 rev 1

All of the following were removed from RFC-002 in the 2026-09-25 revision and
are specified (or re-specified) here:

1. **The governed execution gateway** — `gist_invoke` (MCP) and `POST
   /v1/executions` (REST), execution lifecycle, and reconciliation semantics.
2. **Credential custody** — the encrypted secret store and delegated-OAuth
   connection ownership that RFC-002 rev 1 listed inconsistently (its §2
   excluded a vault while §6 required one; RFC-002 rev 2 owns only the
   connection-*initiation* surface).
3. **The broad provider inventory** — the eight provider families (aggregators,
   SaaS APIs, MCP servers, HTTP/generic, database, code-run, communication,
   file/storage), the per-provider support states (`planned`, `catalog_only`,
   `resolvable`, `executable`, `degraded`, `retired`), and the full adapter
   contract. RFC-002 M1 launches with 3–5 providers; this RFC owns growth
   beyond that, evidence-driven.
4. **Utility billing** — metering, the ledger, and the billing routes, including
   the "never silently switch provider, account, or billing route on retry"
   rule carried from the design-review keep-list.
5. **SSRF and egress controls** for arbitrary provider registration — the
   registry accepts provider records; only the gateway actually calls out.
6. **The original M4/M5 milestones** (rev 1 numbering), renumbered here as
   M-G1 and M-G2 to avoid colliding with RFC-002's M4 (retrieval evaluation).
7. **A publisher-signing / provenance scheme** — RFC-002 §7 blocks public
   distribution until it exists; the design and verification procedure belong
   here (tracked adjacent to, not blocking, the gateway itself).

## 3. Execution model

### Surface

| Endpoint | Contract |
| --- | --- |
| `POST /v1/executions` | Execute a resolved binding: exact skill, capability, tool, binding versions; tenant, principal, and connection references bound server-side |
| `GET /v1/executions/{id}` | Status, result, terminal state |
| `gist_invoke` (MCP) | Same operation on the MCP surface, for clients without direct REST |

An execution request must present a **current resolution** or the pinned
reference tuple. Gist re-verifies at execution time: policy, revocation,
binding currency, connection authority, and scope. A cached resolution never
bypasses re-verification (RFC-002 §6).

### Exactly-once, honestly

- Idempotency keys are bound to tenant, principal, binding, connection, and
  payload; reuse with a changed payload is a conflict, not a silent re-run.
- Gist promises exactly-once **only as far as the provider backs it**. Where the
  provider cannot confirm outcome, the execution record reports
  `unknown_outcome` as a first-class state — never fabricated success, never
  silent retry into a money-moving or mutating side effect.
- A resolution is not an execution grant; an execution grant is created only
  here, at this surface, against current policy.

### Scope boundary: runtimes with their own execution machinery

A consuming runtime that already owns a protected-effects engine (attempt
records, unknown-outcome confirmation states, submission keys bound to
principal/operation, no hidden retries) executes resolved capabilities
through that engine. The gateway is **not** inserted into that path: the
runtime executes, the runtime's approval gate stays the enforcement point,
and the gateway never becomes a second admission layer over an engine that
already provides these guarantees. This surface exists for clients whose
runtime cannot execute a resolved capability (`requires_gateway`).

The state vocabulary here is nevertheless aligned with runtime
protected-effects engines so execution evidence is portable: outcome
confirmation classes (success, failure, accepted-but-unconfirmed,
nonexecution, unknown) and a request-sent distinction (no / yes / unknown)
are the shared vocabulary. An execution record produced by either a runtime
engine or the gateway must carry the same evidence shape; the M-G1 ADR fixes
the exact enum values, and RFC-002 §6's requirement that execution schemas
compile into runtime tool contracts keeps the inputs aligned.

### Approval and human gates

- Capabilities whose `effects` (RFC-002 §11 controlled vocabulary) are
  sensitive route through the consuming runtime's approval gate. The runtime's
  approval machinery remains the enforcement point; the gateway records the
  approval reference and verifies it exists and is unspent before executing.
  **A model-supplied `approved` boolean is not evidence of consent.**
- The gateway never originates approval; it consumes it.

## 4. Credential custody and connection ownership

- The gateway operates credentials it holds, not tokens forwarded from clients:
  Gist access tokens are never provider tokens (kept invariant from RFC-002).
- A delegated-OAuth connection for a direct-API provider **is** refresh-token
  custody and is specified here: encrypted-at-rest store, per-workspace
  scoping, least-privilege grant per binding, rotation, and revocation that
  propagates to bindings and resolutions through the RFC-002 §9 event feed.
- Connection ownership is explicit: every connected account record names the
  workspace, principal, and capability scope it is authorized for; a binding
  may not execute against a connection its resolution was not bound to.
- Provider credential rotation/failure produces `degraded` provider state with
  disclosed loss, not silent fallback to another account or provider.

## 5. Egress, SSRF, and provider-registration controls

Because the gateway performs server-side calls to registered providers:

- Provider endpoints are allowlisted transports (HTTPS only), resolved through
  a DNS/IP policy that blocks private, loopback, link-local, and metadata
  addresses; redirects are re-validated per hop.
- Response size, time, and content-type limits per binding; streaming is
  bounded.
- Result payloads from providers are untrusted content: they pass through the
  same injection screening posture as published packages before reaching any
  model-facing surface, and are never treated as instructions.
- A registered provider record cannot cause the registry to fetch anything at
  publication time; egress exists only on the execution path.

## 6. Billing

- Metered at the execution: binding version, provider route, duration,
  outcome class (`success`, `failed`, `unknown_outcome`).
- The ledger is append-only; billing entries reference the execution record and
  never adjust retroactively without a compensating entry.
- Retries, provider failover, and async completion all append to the same
  execution's ledger trail. Silent route/account switching is prohibited — a
  different provider route is a new, disclosed execution decision.

## 7. Threat model (required before M-G1)

A consolidated threat model is a deliverable of this RFC, not a checklist
deferred to ops. Minimum coverage, drawing on the risks the registry review
flagged:

| Threat | Required control |
| --- | --- |
| Cross-tenant execution / payload confusion | Execution records bound to tenant+principal+connection server-side; isolation mechanism inherits RFC-002 §12 ADR and extends its test matrix to the execution and ledger paths |
| Replay / double-spend | Idempotency binding above; approval references single-use; `unknown_outcome` never auto-retries mutating effects |
| Authority widening | A broader token, swapped cursor, or client-supplied approval id cannot widen scope; audience binding (RFC 8707) extends to the execution surface |
| Credential exfiltration | Secrets never returned on any API; egress policy above; per-binding least privilege |
| Prompt injection via provider results | Untrusted-content posture; screening; no instruction-following from results |
| Revoked binding executes | Event-feed consumption + execution-time re-verification; revocation here is *not* advisory — the gateway is in the loop |
| Ledger tampering | Append-only ledger; compensating entries only; audit of the ledger path |

## 8. Milestones

### M-G1 — Gateway core, credential custody, threat model sign-off

- Execution surface, lifecycle, idempotency/reconciliation, approval-reference
  verification, `unknown_outcome` semantics.
- Credential store and delegated-OAuth connection ownership per §4.
- Egress/SSRF controls per §5.
- The §7 threat model written, reviewed, and signed off. **Gate: no
  executable provider goes live before this.**

### M-G2 — Provider inventory growth and billing

- Grow from the RFC-002 M1 launch set toward the eight-family inventory,
  evidence-driven: each added provider ships its adapter contract, golden
  fixtures, and support state; coverage claims are recorded per provider, never
  aggregate.
- Utility billing per §6, with the ledger live before any billed route.
- Publisher-signing/provenance scheme (§2.7) designed and its verification
  procedure written; on landing, RFC-002 §7's public-distribution block can
  lift.

## 9. Non-goals (inherited)

- Arbitrary hosted shell/Python/Node/Go execution as a general compute service.
- Guaranteeing exactly-once beyond provider guarantees.
- Gist originating approvals or acting as a principal of its own.
- Native-tool hydration or context eviction (never in scope anywhere).

## 10. Decisions required before M-G1

| Decision | Proposed default |
| --- | --- |
| Approval-reference contract with policy-gated runtimes (shape, single-use semantics) | Extend the consuming runtime's approval record; the gateway verifies, never originates |
| Shared execution-evidence vocabulary with runtime protected-effects engines | Align outcome-confirmation and request-sent enum values with the engines at the M-G1 ADR (§3 scope boundary); one evidence shape, two producers |
| Credential store technology and key management | Managed secret store + envelope encryption (e.g. cloud KMS); decide in the M-G1 ADR |
| Billing meter unit and ledger schema | Append-only ledger keyed by execution; meter unit decided with the first billed route |
| Signing scheme for publisher provenance | Sigstore-class transparency record; designed in M-G2 |
